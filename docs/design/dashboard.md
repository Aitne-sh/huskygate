# Dashboard

Web dashboard. Runs as a background daemon and can be operated from the browser.

---

## 1. Getting Started

### CLI Commands

- `huskygate dashboard` / `huskygate dashboard start` — background startup + auto-open browser
- `huskygate dashboard --port 8080` — specify port (default: 3737)
- `huskygate dashboard --no-open` — disable auto-open browser
- `huskygate dashboard --force` — force start (kill stale process if needed)
- `huskygate dashboard stop` — stop daemon
- `huskygate dashboard status` — show dashboard status

Unified commands (server + dashboard):

- `huskygate start` — start both server and dashboard
- `huskygate stop` — stop both server and dashboard
- `huskygate restart` — restart both
- `huskygate status` — show status of both

PID file: `data/dashboard.pid`, log: `data/dashboard.log`

### First-Time Setup Wizard

When the dashboard detects that `SLACK_BOT_TOKEN` is not configured, `GET /` redirects to `/setup` automatically.

The setup wizard (`src/setup/` + `src/dashboard/routes/setup.ts` + `src/dashboard/scripts/setup.ts`) is a standalone HTML page with a 4-step stepper:

1. **Create Slack App** — Opens the Slack App creation page with a pre-filled manifest URL (generated by `src/setup/manifest.ts`)
2. **Install App & Get Bot Token** — User copies `xoxb-` token
3. **Generate App-Level Token** — User creates `xapp-` token with `connections:write` + `authorizations:read` scopes
4. **Set Allowed Users** — Optional comma-separated Slack User IDs

The wizard performs both client-side format validation and server-side live validation (Slack API connectivity check) before persisting.

**Persistence strategy**: Keychain-first. Tokens are stored in the OS Keychain when available, with DB fallback. `ALLOWED_USER_IDS` is always stored in DB.

**Overwrite guard**: If setup is already complete, `POST /api/setup/complete` returns `409 Conflict` unless `force: true` is sent.

**i18n support**: `src/setup/i18n.ts` provides internationalized setup messages.

## 2. Authentication & Security

### Bootstrap Token Flow

1. CLI generates a one-time bootstrap token (`randomBytes(24).toString('base64url')`)
2. Browser opens `http://localhost:<port>/auth#token=<token>` (token in fragment, not query)
3. `GET /auth` serves a minimal HTML page that reads the fragment and POSTs to `/api/auth/bootstrap`
4. Client-side script immediately clears the URL hash via `history.replaceState(null, '', '/auth')` before the fetch, preventing token leakage via browser history or bookmarks
5. Server validates the token via timing-safe comparison, sets an `hg_session` cookie, and invalidates the token
6. Subsequent requests are authenticated via the cookie

Cookie attributes: `HttpOnly; SameSite=Strict; Path=/; Max-Age=<configurable>`. `Secure` is set by default, omitted only when `allowInsecureCookie` is true in development.

### Logout

`POST /api/auth/logout` clears the `hg_session` cookie by setting `Max-Age=0` with matching attributes (`HttpOnly; SameSite=Strict; Path=/; Secure`). Requires both auth cookie and CSRF header. The `Secure` attribute is conditionally included to match the original cookie attributes.

### Route Protection

- `GET /` requires the auth cookie; returns `401` if missing
- All `/api/*` and `/setup` routes require the auth cookie (except `POST /api/auth/bootstrap`)
- After cookie validation, `GET /` checks `isSetupComplete()` and redirects to `/setup` if unconfigured

### CSRF Protection

All mutating API methods (`POST`, `PUT`, `PATCH`, `DELETE`) under `/api/` require the `x-csrf-protection: 1` header. Missing header returns `403 Missing CSRF protection header`.

### Security Response Headers

All responses include the following security headers (set via `res.setHeader()` early in the request handler):

| Header | Value | Purpose |
|--------|-------|---------|
| `X-Content-Type-Options` | `nosniff` | Prevent MIME sniffing |
| `X-Frame-Options` | `DENY` | Prevent clickjacking (legacy browsers) |
| `Referrer-Policy` | `no-referrer` | Prevent URL leakage via Referer header |
| `Content-Security-Policy` | `default-src 'self'; script-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; form-action 'self'; base-uri 'self'` | XSS mitigation, clickjacking prevention (CSP Level 2) |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | HTTPS enforcement (only when `Secure` cookies are enabled) |

Note: `'unsafe-inline'` is required for `script-src` and `style-src` because the SPA inlines all scripts and styles without a bundler. `https://cdn.jsdelivr.net` is required for the Chart.js CDN dependency (SRI-verified). `frame-ancestors 'none'` is the CSP Level 2 equivalent of `X-Frame-Options: DENY`; both are set for backward compatibility.

### Bootstrap Token Rate Limiting

`POST /api/auth/bootstrap` is rate-limited to 5 attempts per 15 minutes per IP. Prevents brute-force of the one-time bootstrap token. The rate limiter performs periodic garbage collection of expired entries (lazy purge on each check, triggered when the window period has elapsed since the last cleanup) to prevent unbounded memory growth.

## 3. Architecture

### SPA Rendering

- The `dashboard` command group in `cli.ts` launches `dashboard-serve` (hidden) as a detached process
- `dashboard-serve` resolves bootstrap config via the shared config resolver, using `.env` only as a compatibility fallback
- The SPA is generated by `renderApp()` in `app.ts`, which assembles:
  - **Styles**: `tokens.ts`, `base.ts`, `components.ts`, `pages.ts`, `orchestrator.ts`, `chat.ts` — all inlined as `<style>` blocks
  - **Layout**: `templates/layout.ts` — HTML shell with sidebar navigation and tab panels
  - **Scripts**: 20+ script modules inlined as a single `<script>` block (no bundler)
  - **CDN**: Chart.js v4.4.7 (SRI-verified) for overview graphs
- Tool icons and logos are embedded as Base64 data URIs in `icons.ts`
- `settings-service.ts` encapsulates patch validation, keychain integration, and hot-reload logic for the settings write path
- `env.ts` provides the `MASK` constant for secret masking
- `yaml.ts` / `toml.ts` provide YAML frontmatter and TOML parsing for skill/config manipulation

### Theming (Light / Dark Mode)

The dashboard supports light and dark themes via a CSS custom-property token system combined with a `data-theme` attribute selector.

#### Token Architecture

All colors, shadows, and glass effects are defined as CSS custom properties in `styles/tokens.ts`:

| Layer | Light `:root` | Dark `darkTokens` |
|-------|---------------|-------------------|
| **Backgrounds** | `--bg: #F5F1E8`, `--bg-subtle: #EDE8DF`, `--bg-card: #fff` | `--bg: #1a1a1a`, `--bg-subtle: #242424`, `--bg-card: #2a2a2a` |
| **Surfaces** | `--surface: rgba(255,255,255,0.52)`, `--glass: rgba(255,255,255,0.52)` | `--surface: rgba(40,40,40,0.7)`, `--glass: rgba(40,40,40,0.85)` |
| **Text** | `--text: #2C2C2C`, `--text-muted: #7A7067` | `--text: #e5e5e5`, `--text-muted: #a0a0a0` |
| **Borders** | `--border: #DDD5C8`, `--glass-border: #DDD5C8` | `--border: #3a3a3a`, `--glass-border: #3a3a3a` |
| **Semantic** | `--green: #16a34a`, `--red: #dc2626`, `--blue: #2563eb` | `--green: #22c55e`, `--red: #f87171`, `--blue: #60a5fa` |
| **DAG Canvas** | `--dag-canvas-bg: #fff`, node fills/strokes (light pastels) | `--dag-canvas-bg: #1e1e1e`, node fills/strokes (dark tints) |

#### Activation Mechanism

Dark mode activates via two CSS paths:

```css
/* System preference (auto) — before JS initialization */
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { ${darkTokens} }
}
/* Explicit toggle — JS sets the attribute */
:root[data-theme="dark"] { ${darkTokens} }
```

On page load, an inline `<head>` script immediately sets `data-theme="dark"` before first render (either from `localStorage` or system preference), preventing FOUC.

Toggle persistence: `localStorage.setItem('huskygate-theme', 'dark' | 'light')`.

#### Dark Override Strategy

Component-level dark mode overrides use `:root[data-theme="dark"]` selectors, consolidated at the end of each style module:

| Style Module | Scope | Dark Override Count |
|-------------|-------|---------------------|
| `tokens.ts` | Design tokens, global reset | Tokens auto-switch via `darkTokens` |
| `base.ts` | Sidebar, main header, cards, buttons, status hero, metrics | ~9 |
| `components.ts` | Page banners, tables, badges, modals | ~18 |
| `chat.ts` | Chat UI, docs panel, tool picker modal | ~24 |
| `pages.ts` | Tasks, logs, settings, skills, webhooks, schedule | ~48 |
| `orchestrator.ts` | DAG editor, panels, runs, guide modal | ~88 |

#### Guidelines for New Components

1. **Use tokens for backgrounds** — `var(--surface)`, `var(--bg-card)`, `var(--bg-subtle)` instead of `#fff`
2. **Use tokens for borders** — `var(--border)`, `var(--glass-border)` instead of `rgba(44,44,44,...)`
3. **Use tokens for text** — `var(--text)`, `var(--text-muted)`, `var(--text-dim)` instead of hardcoded hex
4. **Inline styles in HTML templates** — Must use CSS variables (e.g. `background:var(--surface)`) because inline styles cannot be overridden by `:root[data-theme="dark"]` selectors
5. **Dark overrides** — Append to the "Dark Mode Overrides" section at the end of the relevant style module
6. **Badge contrast** — Dark mode badge text colors must achieve WCAG AA contrast (4.5:1) against their semi-transparent backgrounds on `--bg` (#1a1a1a)

### Data Flow (Query + Command API Client Pattern)

```
Dashboard direct DB/FS (management): session list, Dev Alias, Skills, MCP settings
Server API proxy (execution):        session create/delete, job stop, chat execution
```

- **Read operations (Dashboard -> SQLite direct)**: Session list, audit logs, chat messages, orchestrator list/details, schedule tasks, on-demand tasks, settings, overview stats, chart data, error statistics
- **Write operations (Dashboard -> Server Internal API proxy)**: Session create/delete, job stop, chat send, orchestrator CRUD/execution, task CRUD, webhook/event management, daemon start/stop

### Route Handler Chain

`server.ts` dispatches requests through an ordered handler array. Each handler returns `true` if it handled the request, `false` to continue matching:

```typescript
const handlers = [
  handleSetupRoutes,        // /setup, /api/setup/*
  handleStatusRoutes,       // /api/status, /api/daemon/*
  handleMetricsRoutes,      // /api/metrics
  handleSessionMcpRoutes,   // /api/sessions/:id/mcp-servers*
  handleSessionRoutes,      // /api/sessions*, /api/logs*
  handleSettingsRoutes,     // /api/settings*
  handleChatRoutes,         // /api/chat*, /api/jobs*
  handleDevAliasRoutes,     // /api/dev-aliases*
  handleEventTriggerRoutes, // /api/webhook-endpoints*, /api/event-subscriptions*, /api/triggered-tasks*
  handleMcpRoutes,          // /api/mcp*
  handleOndemandTaskRoutes, // /api/ondemand-tasks*
  handleOrchestratorRoutes, // /api/orchestrators*
  handleScheduleTaskRoutes, // /api/schedule-tasks*, /api/slack/targets, /api/notify
  handleSkillRoutes,        // /api/skills*
  handleFilesystemRoutes,   // /api/filesystem/*
];
```

### RouteContext

All handlers receive a shared `RouteContext` object (defined in `route-context.ts`) providing:

| Field | Description |
|---|---|
| `version` | App version string |
| `dataDir` | Data directory path |
| `workdirRoot` | Working directory root for skills/sessions |
| `dashboardSecret` | Cookie signing secret |
| `serverApiBase` | Server Internal API base URL (`http://127.0.0.1:<port>`) |
| `logPath` | Server log file path (`data/huskygate.log`) |
| `dashboardLogPath` | Dashboard log file path (`data/dashboard.log`) |
| `getDb()` | Lazy-initialized `DashboardDb` accessor |
| `proxyToServerApi()` | JSON proxy to Server Internal API |
| `proxySSE()` | SSE POST proxy to Server Internal API |
| `proxySSEGet()` | SSE GET proxy to Server Internal API |

### Proxy Layer (`proxy.ts`)

Three proxy factories connect the dashboard to the Server Internal API:

- **`createProxyToServerApi()`** — Standard JSON request/response proxy. Authenticates with `Bearer <apiSecret>`. Returns `503` when the server is unreachable.
- **`createProxySSE()`** — SSE POST proxy with backpressure handling. Used for chat send and orchestrator execution streaming.
- **`createProxySSEGet()`** — SSE GET proxy. Used for log streaming and orchestrator run status SSE.

### Server Offline Detection

- `/api/status` checks reachability of the Server Internal API (`/health` endpoint with 2000ms timeout)
- When offline, an offline banner is displayed and mutation buttons are disabled
- When settings change and a restart is required, a restart banner shows the affected keys with Restart/Dismiss buttons

### Port Recovery

On `EADDRINUSE`, the dashboard attempts recovery:

1. Detect the PID holding the port via `findPidOnPort()`
2. Send `SIGTERM` to the stale process
3. Retry `listen()` after 1 second
4. If recovery fails or no stale process is found, exit with a fatal error

### Error Handling

- `uncaughtException` and `unhandledRejection` handlers are attached/detached with reference counting (supports multiple test instances)
- Request-level errors are caught and mapped: `413` for body/file too large, `400` for file type errors, `500` for unhandled errors
- All errors are logged via `dashLog()`

### API Response Envelope

List endpoints (`GET /api/schedule-tasks`, `GET /api/orchestrators`, `GET /api/ondemand-tasks`, etc.) wrap responses in `{ ok: true, data: [...] }` envelope.

## 5. Dashboard API Reference

### Auth (server.ts)

- **POST /api/auth/bootstrap** — Exchange one-time bootstrap token for `hg_session` cookie (unauthenticated, rate-limited)
- **POST /api/auth/logout** — Clear `hg_session` cookie (requires auth cookie + CSRF header)

### Setup (routes/setup.ts)

- **GET /setup** — Standalone HTML setup wizard page (no auth required if already on `/setup`)
- **GET /api/setup/status** — Check if setup is complete (returns `{ complete: boolean }`)
- **POST /api/setup/complete** — Validate tokens + persist (format + live validation, keychain-first). Returns `409` if already configured without `force: true`.

### Status (routes/status.ts)

- **GET /api/status** — Routing: DB direct + Server API health check — Server status, session count, app session stats (per-tool), overview stats, chart data, error statistics (categories, trend, by tool, recent), app tool stats, task summary, sparklines (7-day arrays for sessions, jobs, success rate, errors)
- **POST /api/daemon/start** — Start Server daemon
- **POST /api/daemon/stop** — Stop Server daemon

### Metrics (routes/metrics.ts)

- **GET /api/metrics?range=7d** — Routing: DB direct — Comprehensive analytics data for the Metrics tab. Accepts `range` query param (`24h | 7d | 30d`, default `7d`). Returns `{ ok: true, data: MetricsData }` with: daily job counts, success rate, jobs by source, duration distribution buckets, task summary, orchestration run stats (daily status + avg duration), error analysis (categories, trend, by tool, recent), queue depth (running/pending), and DB size.

### Sessions (routes/sessions.ts)

- **GET /api/sessions** — Routing: DB direct — Session list
- **GET /api/sessions/:id/audit** — Routing: DB direct — Session audit log
- **GET /api/sessions/:id/audit/:jobId/messages** — Routing: DB direct — Job message list
- **GET /api/sessions/:id/trace** — Routing: DB direct — Session execution trace
- **DELETE /api/sessions/:id** — Routing: Server API proxy — Delete session
- **DELETE /api/sessions** — Routing: Server API proxy — Delete all sessions
- **GET /api/logs** — Routing: direct log file read — Log list (limit/offset/level/source). Merges server + dashboard logs when source is `all`.
- **GET /api/logs/stream** — Routing: SSE live tail — Log SSE streaming (polls both server + dashboard log files)

### Session MCP (routes/session-mcp.ts)

- **GET /api/sessions/:id/mcp-servers** — Routing: DB direct — Session-scoped MCP server state
- **PUT /api/sessions/:id/mcp-servers/:serverId** — Routing: DB direct — Toggle session MCP server enabled/disabled
- **DELETE /api/sessions/:id/mcp-servers** — Routing: DB direct — Reset session MCP overrides to defaults

### Settings (routes/settings.ts)

- **GET /api/settings/schema** — Routing: ENV_REGISTRY reference — Settings schema (for UI rendering)
- **GET /api/settings/keychain-status** — Routing: Keychain provider — Keychain availability
- **GET /api/settings** — Routing: ConfigResolver — Current editable settings values (sensitive values masked, source/storage metadata included)
- **PUT /api/settings** — Routing: patch service + ConfigStore + Secure Store + Server API hot-reload — Update changed settings only
- **GET /api/settings/prompts** — Routing: DB + buildInstruction — Tool-specific prompt preview + default instructions
- **PUT /api/settings/prompts/defaults** — Routing: DB direct — Save tool-specific default instructions

Settings write contract:

- Payload is patch-based (`set` / `clear` / `noop`) rather than full-file replacement
- Custom settings panels (for example the Mode toggle card) must translate local UI state into patches without depending on `.settings-input` DOM scraping
- Unknown, internal, and derived keys are rejected
- Keychain-unavailable environments reject secret persistence changes instead of falling back to SQLite plaintext
- Only hot-reloadable keys are forwarded to `/api/settings/apply`

### Chat (routes/chat.ts)

- **GET /api/chat/sessions** — Routing: DB direct — Chat session list (?tool= filter)
- **POST /api/chat/sessions** — Routing: Server API proxy — Create chat session
- **GET /api/chat/:id/messages** — Routing: DB direct — Message list (limit/before pagination)
- **GET /api/chat/:id/messages/new** — Routing: DB direct — New messages (?after= polling)
- **GET /api/chat/:id/status** — Routing: Server API proxy — Session execution status
- **POST /api/chat/:id/send** — Routing: Server API SSE proxy — Send message (SSE streaming response)
- **POST /api/chat/:id/stop** — Routing: Server API proxy — Stop chat job
- **POST /api/chat/:id/upload** — Routing: direct save to workdir — File upload
- **POST /api/chat/:id/tool-approval** — Routing: Server API proxy — Tool approval/denial
- **GET /api/chat/:id/job-stream/:jobId** — Routing: Server API SSE proxy — Job SSE streaming
- **GET /api/chat/:id/artifacts** — Routing: Server API proxy — Artifact list
- **GET /api/chat/:id/artifacts/:jobId/:filename** — Routing: direct workdir file serve — Artifact file delivery
- **POST /api/jobs/:sessionKey/stop** — Routing: Server API proxy — Stop job (sessionKey-based)

Artifact delivery policy:

- Safe raster images (`image/png`, `image/jpeg`, `image/gif`, `image/webp`, `image/bmp`, `image/x-icon`) may render inline in the chat UI
- Active-content artifact types such as `text/html`, `application/xhtml+xml`, and `image/svg+xml` are served as download-only attachments
- Artifact responses send `X-Content-Type-Options: nosniff`; download-only responses also send a sandboxed CSP as defense in depth
- The chat UI must not open non-raster artifacts in a new same-origin tab

Built-in skill policy notes:

- Static metadata (`excludeDirs`, `envVars`, tool variant presence) is discovered from each skill directory's `skill.json` + `SKILL.<tool>.md`
- Built-in skills remain read-only in the unified Skills tab detail; custom skills remain editable
- Custom skills may not declare `envVars`; the dashboard only exposes env-var editing for built-in skills
- Dashboard create routes reject cross-root duplicate `dirName` values to avoid workdir seed collisions
- Masked env values keep the existing secret when submitted unchanged; clearing requires an explicit empty-value action
- Enablement toggles are only valid for tools whose skill variant exists

## 7. Database

The Dashboard shares the same SQLite database with the Server in WAL mode, primarily performing **read-only** access.

### DashboardDb (`dashboard/db.ts`)

- `better-sqlite3` WAL connection (`PRAGMA journal_mode = WAL; PRAGMA busy_timeout = 5000`)
- `ensureSchema()` guarantees the existence of the main schema
- Exposes `ConfigStore` so dashboard-only boot paths and settings routes resolve the same persisted config as the daemon
- Exposes `DevAliasStore`, `DefaultInstructionStore`, `McpServerStore`, `SessionMcpServerStore` for domain-specific CRUD
- Executes read-only queries: session list, audit logs, chat messages, orchestrators, tasks, overview stats, chart data, error statistics, app tool stats, task summary
- Dashboard-specific writes: Dev Alias CRUD, saving default instructions, MCP server CRUD, session MCP allowlist CRUD

## 8. Behavioral Policies

### Slack <-> Dashboard Conversation Sync

Dashboard Chat and Slack chat share the same `dashboard_messages` table, maintaining conversation continuity.

**Sync Policy**:

1. **Message writing**: Unified processing on the Server API side. The `source` field distinguishes the origin (`slack` / `dashboard`)
2. **Session sharing**: Sessions with the same `session_key` are accessible from both Slack and Dashboard
3. **Tool approval**: Slack's `!yes`/`!no` and Dashboard's tool-approval button use the same `pendingApprovals` mechanism
4. **Job execution**: Jobs from Dashboard are submitted to JobQueue as `source: 'dashboard'`. NullMessenger is used to skip Slack output
5. **File attachment**: Dashboard Chat file uploads are saved directly to workdir. Normalized to the same `DownloadedFile` type as Slack attachments

**Constraints**:

- Dashboard Chat can only send messages when the Server Internal API is online
- Slack message edits/deletes are not reflected in Dashboard (append-only)
- Dashboard session creation is done via the Server API, maintaining consistency with the Slack App's session management

### MCP Dashboard Behavior

- All tool tabs edit records in `mcp_servers` and never write back to `~/.claude.json`, `~/.gemini/settings.json`, or `~/.codex/config.toml`
- At execution time HuskyGate materializes generated tool-specific config inside the session workdir:
  - Claude: generated JSON file passed with `--mcp-config ... --strict-mcp-config`
  - Gemini: generated `settings.json` inside `.gemini_runtime_home`
  - Codex: generated `config.toml` inside `.codex_runtime_home`
- This keeps HuskyGate-managed MCP state isolated from user-managed project/global config while still inheriting non-MCP settings read-only where required
- The Docs tab warns that `--setting-sources project` is the Claude default unless `claude_setting_sources` is explicitly overridden in session tool state
- The MCP modal must expose every persisted Codex auth field that survives normalization, including `envHttpHeaders`, so DB-backed edits do not silently drop TOML-only HTTP metadata
- Dashboard MCP API responses must mask secret-bearing header maps for both legacy `headers` and Codex `httpHeaders` / `http_headers` keys before returning them to the browser. `envHttpHeaders` remains unmasked because it stores environment-variable names, not secret values.
- Session MCP checkbox changes apply immediately and are reflected on the next job execution; no Save button is used
- Orchestrator node settings can optionally choose a subset of MCP servers. An empty node selection means "inherit session MCP defaults"

### MCP Secret Masking (`mcp-config.ts`)

Sensitive fields are detected via:

- Field name heuristic (`TOKEN|KEY|SECRET|PASSWORD|API`)
- Header-specific patterns (`authorization`, `proxy-authorization`, `cookie`, `set-cookie`)
- Known container keys (`env`, `headers`, `httpHeaders`, `http_headers`, `oauth`)
- Explicit sensitive fields (`bearer_token`, `client_secret`, `bearerToken`, `clientSecret`)

All matched values are replaced with `***` before sending to the browser.

### Log System (`http.ts`)

- **Structured logging**: `dashLog()` writes JSON lines to stdout, which the shell redirects to `data/dashboard.log`
- **Log reader**: Supports single-file and merged (server + dashboard) log reading with level filtering
- **Large file handling**: If a log file exceeds `MAX_LOG_BYTES`, only the tail is read; the first (likely partial) line is discarded
- **SSE tail**: `createLogTail()` polls multiple log files and emits new lines via callback. Uses `setInterval` polling with configurable intervals and heartbeat.

### Orchestrator Return Modal (`scripts/orchestrator-return-modal.ts`)

Client-side modal for editing orchestrator node return conditions. Exported as an embeddable JavaScript string (`orchestratorReturnModalScript`).

**Capabilities**:
- Summary renderer (`orchRcSummaryHtml`) for inline display of configured return conditions
- Modal open/close lifecycle
- Entry CRUD: `orchRcAddEntry`, `orchRcRemoveEntry`
- Validation: max 20 conditions per node, alphanumeric return values, 2000-char content limit
- Save and sync with backend via PATCH
- Copy-template handler for reusing conditions across nodes

Depends on parent context utilities: `escapeHtml`, `toast`.
